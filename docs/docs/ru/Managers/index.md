# Для менеджеров

## TL;DR

**ContextBrowser** — это внутренний инструмент навигации по коду.
Пока он работает для C# (Roslyn). Планируется TypeScript.

**Зачем поддерживать:**

- 💰 Онбординг нового разработчика сокращается с недель до дней
- 📊 Позволяет видеть покрытие контекстами (аналог test coverage, но для семантики)
- 🔍 Killer feature в будущем — детектор паттернов проектирования
- 🧠 Единственный инструмент, который использует **комментарии самих авторов**,
  а не додумывает за них

**Риски:**

- ⚠️ **Bus factor = 1.** Весь проект держится на одном человеке.
- ⚠️ **Периодически «забрасывается».** Проект долго находился в заброшенном состоянии.
- ⚠️ **Ниша.** Автоматический semantic-анализ — не мейнстрим, требует «своего» человека.
- ⚠️ **Мотивация.** Инструмент не окупается в цифрах, только в качестве жизни команды.

**Что делать:**

1. Выделить **технического владельца** (не только «человек, который написал»).
2. Определить **спонсора** со стороны бизнеса (тот, кто понимает ценность навигации).
3. Фиксировать **квартальные цели** — не давать проекту зарастать.
4. Периодически **демонстрировать** команде новые отчёты (это мотивирует).

---

## Почему это важно

### Проблема

Кодовая база растёт быстрее, чем команда. Каждый новый разработчик — 2–4 недели
онбординга. Автор кода помнит, что он делал, но **не помнит где это лежит**.

Обычные инструменты не решают:

| Инструмент | Что даёт                    | Чего не даёт               |
| ---------- | --------------------------- | -------------------------- |
| IDE        | автодополнение, jump-to-def | нет семантической карты    |
| grep       | поиск текста                | нет связей, нет контекстов |
| SonarQube  | качество, баги              | нет навигации по смыслу    |
| Confluence | документация                | устаревает мгновенно       |
| XML-docs   | API-документация            | ручная, фрагментарная      |

**ContextBrowser даёт:** автоматическую карту того, **что делает** код,
собранную из **авторских комментариев**.

### Ценность

- **Онбординг.** Новый разработчик открывает отчёт, видит `create × roslyn` —
  сразу понимает, где искать создание контекстов.
- **Code review.** Рецензент видит, какие actions задеты в PR.
- **Архитектура.** Видно, где дублируется логика по action/domain.
- **Метрика.** Покрытие контекстами — прокси-метрика «зрелости» проекта.

### Визуально

```
   Без ContextBrowser                С ContextBrowser
   ──────────────────                ────────────────

   .cs файлы            .cs файлы         .cs файлы
      │                    │                  │
      ▼                    ▼                  ▼
   "где искать?"         grep             отчёт с картой
   "что делает?"         "не помню"          │
   "кто вызывает?"       jump-to-def        ▼
   "как связано?"        "попробую угадать" "вот create × roslyn"
   ──────────────────    ─────────────────  ──────────────────
   2–4 недели онбординга  20 минут поиска     5 секунд
```

## Что просить у команды

### Каждую неделю

- Обновлять `docs/release/in-progress.md`
- Не давать «затихнуть» больше двух недель

### Каждый месяц

- Демонстрация новых отчётов (5–10 минут на общем звонке)
- Метрика: сколько новых контекстов добавлено

### Каждый квартал

- Ревизия `docs/release/backlog.md` (что умерло, что выросло)
- Обновление этого документа
- Разговор с владельцем: что болит, что хочется

### Раз в год

- Оценка: помогает ли инструмент новым разработчикам?
- Метрика: время онбординга (опрос новичков)
- Решение: продолжать / пивотировать / закрыть

## Метрики (то, на что смотреть)

| Метрика                | Где смотреть                 | Целевое значение |
| ---------------------- | ---------------------------- | ---------------- |
| Покрытие контекстами   | отчёт HTML                   | > 60%            |
| Время онбординга       | опрос новичков               | < 1 неделя       |
| Число языков           | `docs/01-goals.md`           | ≥ 2              |
| Bus factor             | эта страница                 | ≥ 2              |
| Частота обновлений     | `git log --since="3 months"` | ≥ 1 раз/месяц    |
| Точность графа вызовов | тесты на реальных проектах   | > 95%            |

### Как измерять покрытие

1. Запустить `ContextBrowser --project <имя>` на целевом проекте.
2. Открыть `output/<проект>/site/index.html`.
3. Посмотреть, сколько ячеек заполнено (heatmap покажет непокрытые).
4. Целевое: > 60% классов/методов имеют пару `(action, domain)`.

### Как измерять время онбординга

Через месяц после найма нового разработчика спросить:
- «Сколько времени ты потратил на понимание архитектуры?»
- «Использовал ли ты ContextBrowser для навигации?»
- «Помогло ли? На сколько дней сократило?»

## Что делать в случае проблем

### «Проект заброшен»

1. Найти **владельца** (см. ниже)
2. Дать ему 20% времени на поддержку
3. Спонсору — не требовать «бизнес-ценности», достаточно «quality of life»
4. Начать с малого: одна задача в месяц, не «полный рефактор»

### «Владелец уходит»

1. **Немедленно** назначить нового
2. Дать новому 2 недели на «вхождение в контекст» (см. метафору!)
3. За это время — написать недостающие документы
4. Первое время новый владелец работает в паре со старым (даже удалённо)

### «Надо быстро показать пользу»

1. Взять **самый грязный** проект команды
2. Прогнать `ContextBrowser --project <that-project>`
3. Показать отчёт: «вот так он выглядит»
4. Повторить через месяц, показать динамику
5. Если динамика положительная — закрепить как регулярный ритуал

### «Спонсор сомневается»

Задать три вопроса:

1. «Сколько стоит месяц онбординга нового разработчика?»
2. «Сколько разработчиков приходит в год?»
3. «Сократит ли ContextBrowser это время вдвое?»

Если ответ «да» на третий — окупаемость очевидна.

## Метафора для объяснения (полезна на защите)

> Представьте, что у вас есть большая библиотека. Книги (классы) стоят
> на полках (namespaces), но каталога нет. Вы можете найти книгу только
> по корешку (имени файла).
>
> **ContextBrowser** — это **каталог**. Он не переписывает книги, он просто
> читает **закладки**, оставленные авторами, и строит карту: «вот раздел
> `create`, вот раздел `roslyn`, они пересекаются здесь».
>
> Без каталога библиотека работает. С каталогом — **работает в 10 раз быстрее**.

### Дополнительная метафора (для скептиков)

> `// context: create, loader` — это как закладка в книге.
> Автор уже знает, что эта функция — «создание загрузчика».
> Он оставил закладку. ContextBrowser собирает все закладки в одну карту.
>
> Это **не ИИ**, это **не магия** — это простое чтение того, что автор
> сам уже написал. Но собранное в одном месте и показанное наглядно.

## Что НЕ надо говорить владельцу

- ❌ «Давайте использовать X вместо Y» — без контекста
- ❌ «Почему это не готово?» — если это не в roadmap
- ❌ «Нужно больше тестов» — если нет времени на них
- ❌ «Это же легко, добавьте ещё...» — оценка только от владельца
- ❌ «А вот в [другом проекте] сделали...» — сравнение без контекста

## Что надо говорить

- ✅ «Покажи последний отчёт, давай обсудим»
- ✅ «Дай мне 3 задачи, которые тут можно закрыть без контекста»
- ✅ «Что нужно, чтобы это работало на новом проекте?»
- ✅ «Сколько времени тебе надо на это? Я защищу перед спонсором»
- ✅ «Что тебя блокирует? Как я могу помочь?»

## Что делать, если проекта нет, а нужен

Если ContextBrowser ещё не поддерживается, но команда болит — начать с
**пилотного проекта**:

1. Выбрать **один** самый грязный проект команды
2. Поручить владельцу (даже если это временно) сделать первый отчёт
3. Показать команде: «вот так он выглядит»
4. Спросить команду: «полезно?»
5. Если «да» — продолжать. Если «нет» — остановиться.

**Не надо:** «сначала сделать идеально, потом показать». Первый отчёт — за 1 день.
